savannah / how it works

One board for every Claude Code session you have open.

Savannah is two things that share a name and a repository. The first is a terminal board that keeps your own interactive Claude Code tabs in order on one machine. The second is a mesh that lets Claude on one machine ask Claude on another, carried by song. This page shows each as it works today, and then what joining them across machines would take.

01 / THE TWO LAYERS

What exists today

Both layers work now. They are separate: the board does not use song, and the mesh does not manage your tabs.

Works today / one machine

The board and work sessions

Bare savannah opens the board. Each task is a work session: one named iTerm2 tab with your ordinary interactive claude in a git worktree above and a shell in the same worktree below, plus a plain-text notes file.

  • No daemon, no song, and the tool itself spends no tokens.
  • macOS and iTerm2 only (3.5 or newer, Python API on).
Works today / one LAN

The mesh

Every machine runs savannahd, a small C++20 daemon that exposes that machine's headless Claude as a typed, streamed, supervised song service. Nodes find each other by mDNS and authenticate with a shared key.

  • Acceptance run on a real LAN: macOS arm64 and Ubuntu x86_64, asks in both directions.
  • No forked Claude Code, no broker, no cloud relay.
02 / ONE MACHINE

How the board knows what every tab is doing

There is no server. The board, the command line, your scripts and Claude itself all go through one command, and everything it knows is files on disk.

Each row on the board is a record joined, at read time, with the status file of the live Claude Code session in that worktree.

What a row tells you

waiting: blocked on a permission prompt or your answer

working

idle or done

Where a row sits

Sections you order yourself: NOW, ACTIVE and LATER. Code reviews get their own REVIEWS section, and closed sessions go to HISTORY.

One key for each chore

Ctrl-N new task, Enter jump to its tab or type into its Claude, Ctrl-O what it said, Ctrl-T a note, Ctrl-A twice asks every idle tab what it is doing.

The same door for automation

A script opens a review session with one repeatable call. It returns the session that is already there instead of making a second, and it leaves the tab you are on selected.

savannah work new pr-2353 --repo ~/ng/zfs --mode review --target 2353 \
    --if-absent --background --json
03 / TWO MACHINES

The mesh, carried by song

Stock Claude Code gets an ask_peer tool. When it calls it, the question travels over song to another machine's daemon, which runs a headless Claude there and streams the answer back.

savannah ls lists every node on the network, savannah ask <name> asks one, savannah task ... runs persistent headless workers, and savannah mesh is the board for them.

Stated limits of the mesh today: one ask at a time per node, cancel is a kill and not cooperative, prompt out and text back with no file transfer, nothing migrates a session between machines, and the traffic is authenticated but not encrypted. The README says to treat the mesh as LAN-trust.
04 / THE SUBSTRATE

Why song

Song (Services Over Native Gateways) is a C++20 service framework: you describe a service in an IDL file, songc generates type-safe C++ and Python code, and services talk over pipes or TCP. Savannah's daemon is a song service. The figures below are song's own, from its README.

705tests: 598 unit and 107 integration
0warnings allowed: -Wall -Wextra -Werror on clang and GCC
16 Bfixed header on every message
~31Klines of C++20, no external dependencies for the core
Security, built in

Two layers, both part of song

  • HMAC-SHA256 authentication. A tag on every message, constant-time comparison, a wrapper over any transport. Platform crypto: CommonCrypto on macOS, OpenSSL on Linux. This is what savannah uses today.
  • TLS encryption. Certificate or pre-shared-key mode, via mbedTLS (an optional dependency; song builds without it). Savannah does not use it yet.
  • Size limits on every message (16 MB), and fuzz harnesses for the wire and buffer decoders.
Speed, measured

Song's own numbers

Buffer encode and decode12 ns
Pipe RPC round trip~6 us
TCP round trip, localhost~100-200 us
Service start (fork, exec, handshake)~100 ms

Apple M4, release build, from song's README. In savannah an ask is bounded by how long Claude takes, not by the wire.

05 / WHERE THIS GOES

Sessions on many machines, on one board

The direction: the board that organises your Claude sessions on one Mac organises them on every machine you use, with song carrying the traffic between them. Part of that already exists and part does not. This section separates the two.

To get thereTodayStill needed
Reach a Claude on another machine Works on a LAN: mDNS discovery by name, or --addr HOST:PORT directly. Nothing for a LAN. Beyond it, see the rows below.
See another machine's sessions on your board The mesh board shows headless task workers per node. Interactive tabs are local only. A way for a node to report its own work sessions, and a board that lists them. The roadmap already names live status pushed through song's properties in place of polling.
Encryption on the wire Savannah authenticates with HMAC and does not encrypt. Song's TLS transport exists and is tested. Wire song's TLS (the design names TLS-PSK) into savannahd and the CLI. The design marks this as required for anything beyond the LAN.
Find nodes outside the LAN mDNS does not leave the local network. Song ships a registry service for other subnets. Song's registry example has no ownership or authorization and binds loopback by default; its README says a production registry needs both.
Get through routers and firewalls Savannah is direct TCP between nodes, with no broker and no relay, by design. Nodes must be able to reach each other: a VPN or an overlay network would give that without changing the design. Nothing in the repository does this today.
Other terminals and systems Work sessions need macOS and iTerm2. A tmux terminal behind the existing terminal seam is on the roadmap.
One honest caveat from song itself: its README places it at same-host and LAN-scoped communication where you control both ends, and recommends gRPC for internet-facing services. Its 8-byte HMAC tag is sized for that setting. Running savannah across the world means running it over TLS between machines you own, not exposing a node to the open internet.
